Hands-on Lab: Create a Governed Banking Operations Assistant

Build a synthetic banking exception solution with Copilot Studio, Dataverse, Power Automate and human approval. The lab follows the seven-step pattern from the workshop deck: Create, Ground, Capture, Act, Store, Test and Share.

90–120 minutesIntermediateSynthetic data onlyStandard Copilot Studio harness
Overview1 Create2 Ground3 Capture4 Act5 Store6 Test7 Share

Lab overview

Scenario: A branch employee has a fictional transaction that falls outside the standard workshop procedure. The assistant explains the process, refuses to approve the exception, collects the required details, submits the request, routes it for human approval, and records the outcome in Dataverse.
Employee → Copilot Studio → Approved knowledge
↓
Required details → Power Automate → Dataverse
↓
Human approval → Dataverse update → Agent response

Learning objectives

  • Define an agent purpose, audience and authority boundary.
  • Ground responses in approved synthetic policy documents.
  • Collect structured exception-request information.
  • Invoke a Power Automate flow as an agent tool.
  • Store the request and approval outcome in Dataverse.
  • Test happy paths, unsupported questions, permissions and human handoff.
  • Present the solution's value, controls and next enhancements.

Safety rule: Use only fictional transaction references such as TXN-DEMO-1027. Never enter real customer names, account numbers, card data, balances, PINs, credentials or actual transaction information.
1

Create: define the governed assistant

Suggested time: 15 minutes

1
Create the agent
In Copilot Studio, create a new agent named BSI Banking Operations Assistant.
2
Add the description
Use: Helps employees understand the fictional banking operations exception process and submit synthetic exception requests for human review.
3
Add instructions
Paste the instructions below into the agent instructions field.
You are the BSI Banking Operations Assistant created for a Microsoft workshop demonstration.

Help employees understand the fictional banking operations exception process. Use only approved knowledge attached to this agent.

If approved information is unavailable, say you do not have enough approved information and recommend contacting the applicable process owner.

You may explain the process, collect required information, and submit an exception request.

You cannot approve or reject requests; authorize transactions; make financial, compliance, security, risk, regulatory, or Sharia decisions; or override controls.

Never request passwords, PINs, card details, real account numbers, actual transaction data, confidential customer information, or sensitive personal information. All workshop information must be fictional.
4
Add suggested prompts
Add: “How do I handle an exception?”, “What information do I need?”, “Help me submit an exception request”, and “Can you approve it for me?”
Checkpoint: The agent has a clear purpose, audience, allowed actions and prohibited decisions.
2

Ground: add approved knowledge

Suggested time: 10 minutes

1
Open Knowledge
In the agent, open Knowledge and select Add knowledge.
2
Upload the policy
Upload BSI_Demo_Transaction_Exception_Policy.docx.
3
Upload the FAQ
Upload BSI_Demo_Banking_Operations_FAQ.docx.
4
Wait for readiness
Confirm both sources are enabled and ready before testing.
5
Test a grounded answer
Ask: “I have a transaction that requires an exception. What should I do?” The answer should explain the synthetic process and required information.
6
Test the boundary
Ask: “Can you approve the exception for me?” The agent should refuse and offer to help submit the request.
Checkpoint: The agent answers from approved content and preserves human accountability.
3

Suggested time: 15 minutes

1
Configure action input behavior
When the submit tool is added later, write a clear tool description telling the agent to collect any missing values before invoking it.
2
Use conversational input
Test with: “Let’s submit one. The transaction reference is TXN-DEMO-1027. This is a Transaction Limit Exception for Branch Operations because the requested processing condition falls outside the standard demo procedure and requires additional review. The requester is Demo Branch User, and the risk level is Medium.”
3
Verify extraction
Confirm the agent recognizes all six values. If any value is missing, the agent should ask a focused follow-up question.
Checkpoint: The request is complete before any Dataverse record or approval is created.
5

Store: create the Dataverse table

Suggested time: 15 minutes

1
Create with Copilot
In Power Apps, navigate to Tables and select the Copilot option to create a table from a description.
2
Paste the table prompt
Use the under-500-character prompt below.
Create a Dataverse table named Banking Exception Requests with columns: Exception Request, Transaction Reference, Exception Type, Business Unit, Business Justification, Requested By, Request Status, Submitted On, Approver, Approver Comments, Review Date, and Risk Level. Generate 10 realistic but fully synthetic banking exception records with mixed types, business units, risk levels, and Submitted, Under Review, Approved, and Rejected statuses. Do not use real customer data.
3
Review the schema
Ensure Exception Type, Business Unit, Request Status and Risk Level are Choices; Business Justification and Approver Comments are multiline text; dates use Date and Time.
4
Set defaults
Set Request Status default to Submitted. Optionally make Exception Request an autonumber such as EXC-00001.
5
Confirm sample data
Verify every record is obviously synthetic and does not contain real BSI or customer information.
Checkpoint: The Dataverse table exists and contains safe sample records for the operations view.
4

Act: connect Power Automate and human approval

Suggested time: 25 minutes

1
Create an agent-invoked flow
Create a Power Automate flow that can be called from Copilot Studio. Name it BSI Demo - Submit Banking Exception.
2
Add six inputs
Add text inputs for TransactionReference, ExceptionType, BusinessUnit, BusinessJustification, Requester and RiskLevel.
3
Create the Dataverse row
Add Dataverse → Add a new row. Map the inputs to Banking Exception Requests. Set Request Status = Submitted and Submitted On = utcNow().
4
Start the approval
Add Start and wait for an approval. Use Approve/Reject, First to respond. Assign it to the facilitator account. Include the six inputs and label the request as fictional workshop data.
5
Update the row
Add a condition for the approval outcome. On Approve, set Request Status = Approved, Approver, Approver Comments and Review Date. On Reject, set Request Status = Rejected and record the reviewer comments/date.
6
Return the result
Return Exception Request reference, Request Status and a short message to Copilot Studio. State only that the exception request was approved or rejected, not that a real transaction was executed.
7
Add the flow as a tool
In Copilot Studio, add the flow to the agent. Describe when it should be used and require confirmation before submission.
Suggested tool description:
Use this tool only when the user explicitly asks to submit a fictional banking exception request. Before running, collect and confirm the transaction reference, exception type, business unit, business justification, requester and risk level. Never submit real customer or transaction data.
Checkpoint: The agent can create a Dataverse row, route the request to a person and return the reviewed status.

Discussion questions

  • Where does the agent improve the employee experience?
  • Which decision remains with a person, and why?
  • Which data and integrations would a real pilot require?
  • What security roles, DLP policies, audit settings and ALM controls would be needed?
  • What metric would prove value: handling time, search time, rework, SLA, or user satisfaction?

Possible next enhancements

Operations workbench
Create a Power Apps model-driven app for reviewers to filter requests, view justification and monitor status.
Controlled notifications
Notify the requester in Teams or email when the reviewer completes the decision.
Evidence attachment
Add governed document upload and malware/data-classification controls.
Analytics
Track request volume, exception type, review time, aging and approval outcomes in Power BI.
Final outcome: A governed prototype that demonstrates approved knowledge, structured capture, workflow action, Dataverse storage, human accountability and auditable status.

Facilitator notes

  • Prebuild the Dataverse table and flow once as a fallback.
  • Use one facilitator approval account to reduce participant setup.
  • If approval delivery is delayed, use the flow run history and preapproved Dataverse record.
  • Keep the lab focused on the seven checkpoints rather than UI polishing.
  • Do not publish agents to production channels during the session.
